# Решения и компромиссы

Коротко: что выбрано, почему и чем за это заплачено. Всё, что здесь названо
проверенным, воспроизводилось на стенде; ссылки на замеры — в [performance.md](performance.md).

### CDC через Debezium, история — через JDBC

Коннектор стартует с `snapshot.mode=no_data`: создаёт слот репликации и читает
только изменения. Историю (55,6 млн строк) забирает Spark через JDBC —
параллельно по 12 диапазонам `txn_id`, за 196 с. Снимок Debezium шёл бы одним
потоком через Kafka и занял бы на брокере место под все 55 млн событий.

Цена — стык между выгрузкой и потоком. Слот создаётся до выгрузки, поэтому
строка, изменённая в промежутке, приходит дважды. Это безопасно благодаря
правилу версий: у каждой строки источника `row_version` (триггер), событие
применяется, только если его версия больше текущей, а удаление получает
`before.row_version + 1`. Для этого у таблиц `REPLICA IDENTITY FULL` — иначе в
событии удаления был бы только ключ.

Почему не загрузка по водяному знаку `updated_at`, как в retail-dwh: она не
видит удалений. А в процессинге удаление — обычное событие (снятый холд).

### JSON без Schema Registry

Конвертер JSON без встроенной схемы. raw хранит событие как есть, схему задаёт
`spark/pyspark/tables.py`. Новая колонка в источнике не ломает raw, а в ods её
надо добавить руками. С Avro и Schema Registry эволюция схем была бы строже, но
это ещё один сервис в 8 ГБ памяти.

### Kafka Connect из образа Kafka, а не debezium/connect

Образы `debezium/connect` на Docker Hub остановились на 3.0.0 (октябрь 2024).
Воркер собран из `apache/kafka:4.2.2` и плагина Debezium 3.7.0 с Maven Central —
это десять строк Dockerfile.

### Spark 3.5 и Hive Metastore 3.1, а не 4.x

У ветки Spark 3.5 продлённая поддержка (extended LTS) до ноября 2027 года —
её оставили специально на время миграции на 4.x. Scala 2.12. Внутри Spark 3.5
клиент Hive 2.3.9, и Iceberg `HiveCatalog` ходит в Metastore именно им. Этот
клиент вызывает Thrift-метод `get_table`, которого нет в Metastore 4.0+:
проверено на 4.0.1 и 4.2.1, ответ — `Invalid method name: 'get_table'`.
Metastore 3.1.3 работает с ним без проблем.

Следствие: HiveServer2 3.1 не читает Iceberg 1.12, таблицы ods читает Spark.
HiveServer2 нужен для raw — классических Hive-таблиц с партициями.

### Iceberg merge-on-read и ежедневное обслуживание

MERGE каждый час меняет немного строк. При copy-on-write он переписывал бы
целые файлы (по 70 МБ на месячную партицию), при merge-on-read — пишет
маленькие файлы удалений. Платой становится обслуживание:
`rewrite_data_files` применяет удаления и сливает мелкие файлы,
`expire_snapshots` освобождает место. Нашлась тонкость: файл удалений, чей
файл данных уже переписан, остаётся в метаданных, пока не попросить
`remove-dangling-deletes`.

### MERGE с отсечением партиций

`ON t.txn_id = s.txn_id` заставляет MERGE читать все партиции таблицы. Время
операции не меняется, поэтому к условию добавлено
`t.txn_ts >= <самая ранняя операция в пакете>` — MERGE читает только свежие месяцы.

### Партиции Iceberg считаются в UTC

`months(txn_ts)` для `timestamp with time zone` берёт месяц в UTC. Операции
первых пяти часов 1 января 2025 по Алматы (UTC+5) легли в партицию декабря 2024 —
там 544 строки, хотя история начинается с января. Для отсечения партиций это
не мешает, но важно при ручном выборе партиций.

### YARN: две очереди и доля под AM

Очереди `etl` (гарантировано 70 %) и `adhoc` (не больше 50 %): регламентная
загрузка не ждёт аналитиков. По умолчанию Application Master может занять 10 %
очереди — около 200 МБ, драйвер Spark в режиме cluster в это не помещается;
доля поднята до 50 %.

### Scala для выгрузки фактов

Самая тяжёлая задача (55 млн строк, пять соединений) написана на Scala: так она
выглядит в банках, где Spark-код часто на Scala, а тестируется ScalaTest с
локальным Spark. Остальные задачи на PySpark.

### Greengage вместо Greenplum

Исходники Greenplum закрыты в 2024 году. Greengage — открытый форк от Arenadata
на базе Greenplum 7 (PostgreSQL 12). Образ `woblerr/greengage` собран
сообществом; в нём есть PXF.

### PXF для загрузки

Каждый сегмент Greenplum читает свою часть Parquet из HDFS сам, мастер данные
не пропускает. 55,6 млн строк — 200 с. Выгрузка грузится одной транзакцией
вместе с записью в журнал: упавшая загрузка откатывается целиком и
повторяется.

Проверено, что время не съезжает: Spark пишет `timestamp` в Parquet как INT96
(UTC), PXF отдаёт его в `timestamptz` с тем же моментом до микросекунды.

### dbt-postgres с одним переопределённым макросом

Адаптер dbt-greenplum не обновлялся с мая 2023 года. Greengage 7 говорит на
диалекте PostgreSQL 12, поэтому достаточно dbt-postgres и своей версии
`postgres__create_table_as`: распределение, колоночное хранение и партиции
задаются в конфиге модели. CREATE TABLE AS не умеет партиции — макрос создаёт
пустую таблицу нужной формы и заливает её отдельно.

### SCD2 по времени изменения, а не загрузки

Snapshot по стратегии `check` (новая версия только при смене города или
сегмента, а не телефона), но `valid_from` берётся из `updated_at` источника.
Иначе операции между изменением и ближайшим запуском dbt получили бы старый
сегмент. Первая версия каждого клиента открыта с 1900 года: истории до первой
загрузки у нас нет, а без этого ранние операции не нашли бы версию в
соединении по интервалу.

### Инкрементальные витрины

Сначала витрины пересобирались целиком каждый час (7 минут из 12,5 на цикл).
На стенде это оказалось не просто долго: пока Greenplum строил две витрины
параллельно, у виртуальной машины кончался страничный кэш, диск уходил в
перечитывание (Greenplum прочитал 520 ГБ за полтора часа), и API-сервер Airflow
переставал отвечать. Теперь витрина хранит `src_export_id` — последнюю
выгрузку, на которой построена, и пересчитывает целиком только дни или месяцы,
куда пришли новые строки факта (delete+insert по периоду). Пересчёт периода
целиком, а не по ключу клиента, нужен, чтобы ушла и строка клиента, у которого
в месяце всё отменили.

### Персональные данные остаются в ods

ФИО, телефон, e-mail и дата рождения есть в ods (как в источнике), но в
Greenplum не выгружаются: вместо даты рождения — год. Тест
`test_fact_columns_have_no_personal_data` проверяет список колонок выгрузки.

### Airflow: spark-submit в режиме cluster

Драйвер работает в YARN, в Airflow только клиент. Провайдер Spark 6.3 сохраняет
id приложения в состоянии задачи: если воркер Airflow упадёт, повтор задачи
дождётся уже запущенного приложения, а не отправит его второй раз. Для этого
нужен REST API ResourceManager (`yarn_track_via_rm_api`).

### Допуск heartbeat в Airflow

В Airflow 3 задача сообщает о себе API-серверу; после трёх неудачных heartbeat
(по 5 с на запрос) супервизор убивает её. На стенде, где все сервисы делят один
диск, API однажды не отвечал около четырёх минут — dbt был убит посреди сборки.
Допуск поднят: 10 heartbeat по 30 с, порог зомби-задачи в планировщике — 15 минут.
В продакшене правильнее развести API-сервер и тяжёлые базы по разным машинам.

### Ресурсы

Стенд работает в 8 ГБ Docker, поэтому сервисы разбиты на профили compose, а
YARN получает 3 ГБ. HDFS с одной DataNode и репликацией 1 — это проверка
логики, а не отказоустойчивости.
