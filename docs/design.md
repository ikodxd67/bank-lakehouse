# Дизайн

## Зачем этот проект

Три прошлых проекта закрывают Airflow, ClickHouse, Data Vault, Oracle, Kafka и
Spark на небольших объёмах. В вакансиях банков и телекома (замер на hh.ru,
октябрь 2026, 38 вакансий дата-инженера) есть то, чего там нет:

| Что | Упоминаний из 38 |
|---|---|
| Hadoop (HDFS, YARN) | 17 |
| Greenplum | 15 |
| Scala | 12 |
| Hive | 8 |
| Iceberg | 8 |
| dbt | 8 |

Отсюда стек: HDFS и YARN, Hive Metastore и HiveServer2, Spark на YARN (одна
задача на Scala), Iceberg, Greenplum (форк Greengage), dbt. Плюс CDC через
Debezium: он редко упоминается в тексте вакансий, но это обычный способ
забирать данные из OLTP банка, и он закрывает главный недостаток загрузки по
водяному знаку — удаления в источнике не видны.

## Предметная область

Процессинг банковских карт. Источник — OLTP-база (PostgreSQL), схема `core`:

- `clients` — клиенты, меняются адрес, телефон, сегмент;
- `accounts`, `cards` — счета и карты, карты блокируются и перевыпускаются;
- `merchants` — торговые точки с MCC;
- `card_transactions` — операции: `authorized` → `posted` или `reversed`.
  Авторизация, которая не подтвердилась за 7 дней, удаляется из OLTP (холд
  снят). Это единственный источник удалений, и он настоящий: так делают
  процессинговые системы, чтобы таблица холдов не росла;
- `fx_rates` — курсы казначейства.

У каждой строки есть `row_version` (растёт на каждом UPDATE, триггер) и
`updated_at`. Версия нужна, чтобы начальная выгрузка и поток CDC склеивались
без потерь и дублей (см. ниже).

Объём: около 50 млн операций за январь 2025 — сентябрь 2026. Распределения
нарочно перекошены: один маркетплейс даёт около четверти всех операций, у
части клиентов корпоративные карты с сотнями операций в день. На этом перекосе
показывается настройка Spark и выбор ключа распределения в Greenplum.

## Поток данных

```
core (PostgreSQL, logical replication)
  │  начальная выгрузка: Spark JDBC, параллельно по диапазонам txn_id
  │  дальше: Debezium → Kafka (топик на таблицу)
  ▼
raw (HDFS, Parquet, внешние таблицы Hive)      ← Spark Structured Streaming, availableNow
  ▼
ods (Iceberg в HDFS, каталог — Hive Metastore) ← Spark MERGE по row_version
  ▼
export (HDFS, Parquet)                          ← Spark-задача на Scala: обогащение фактов
  ▼
Greenplum: stg (внешние таблицы PXF) → dds (звезда) → marts   ← dbt
```

Оркестрация — Airflow 3, Spark запускается на YARN в режиме `cluster`.

## Склейка начальной выгрузки и CDC

Коннектор Debezium стартует с `snapshot.mode=no_data`: он создаёт слот
репликации и читает только изменения после этого момента. Сами данные забирает
Spark через JDBC. Выгрузка начинается после создания слота, поэтому строки,
изменённые в промежутке, попадут и в выгрузку, и в поток. Правило применения в
`ods` одно на всех: событие применяется, только если его версия больше
текущей. Удаление получает версию `before.row_version + 1`, чтобы оно
побеждало любое более раннее состояние строки. Для этого у таблиц в источнике
`REPLICA IDENTITY FULL`: в событии удаления есть вся строка, включая версию.

## Где что лежит в HDFS

```
/data/raw/cdc/<table>/dt=YYYY-MM-DD/   события CDC как есть (Parquet)
/data/raw/snapshot/<table>/            начальная выгрузка
/warehouse/ods.db/<table>/             Iceberg
/data/export/fact_card_txn/            выгрузка для Greenplum
/spark/                                 архив jar-ов Spark для YARN, логи событий
```

## Решения, которые нужно будет защищать

- **Spark 3.5, а не 4.x.** Ветка 3.5 — последняя в 3.x и основная в
  продакшене банков; Scala 2.12.
- **Hive Metastore как каталог Iceberg.** Так таблицы видны и Spark, и
  HiveServer2, и Trino без отдельного REST-каталога.
- **PXF для загрузки в Greenplum.** Сегменты читают Parquet из HDFS параллельно,
  без прохода через мастер. Сравнивается с записью из Spark через JDBC.
- **dbt-postgres со своими макросами вместо dbt-greenplum.** Адаптер
  dbt-greenplum не обновлялся с мая 2023 года; распределение и колоночное
  хранение добавляются переопределением одного макроса.
- **Ресурсы.** Весь стенд должен работать в 8 ГБ памяти Docker, поэтому
  сервисы разбиты на профили compose, а YARN получает 3 ГБ.
