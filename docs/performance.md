# Замеры

Стенд: ноутбук, Docker с 8 ГБ памяти, YARN — одна NodeManager на 3 ГБ и 4 ядра,
Greenplum — два сегмента в одном контейнере. Цифры одиночных прогонов: разницу
в 10–15 % между ними не стоит считать закономерностью.

## Объёмы

| | |
|---|---|
| Источник, `core.card_transactions` | 55,6 млн строк, 7,4 ГБ в PostgreSQL |
| ods, Iceberg + zstd | 1,6 ГБ, по файлу ~73 МБ на месячную партицию |
| Выгрузка фактов, Parquet | 2,0 ГБ, 21 файл |
| Факт в Greenplum, AO column + zstd | 1,6 ГБ |

## Загрузка

| Шаг | Время | Скорость |

| Начальная выгрузка JDBC → Iceberg, 12 потоков | 196 с | 283 тыс. строк/с |

Почасовой цикл в Airflow (≈ 45 тыс. изменений за час): cdc_to_raw 63 с,
raw_to_ods 85 с, факт 103 с, справочники 54 с, загрузка в Greenplum 14 с, dbt
около 7 минут (витрины пересобираются целиком), сверка 30 с — 12,5 минуты.

## Перекос в соединении с ТСП

Маркетплейс (`merchant_id = 1`) — четверть всех операций. Полная выгрузка фактов,
55,6 млн строк, четыре стратегии соединения (`scripts/bench_skew.sh`). Цифры из
Spark History Server (`scripts/spark_stages.py`).

| Стратегия | Приложение | Задач в стадии соединения | Самая долгая задача / медиана | Shuffle |
|---|---|---|---|---|
| none — sort-merge join | 204 с | 33 | 48,6 с / 5,3 с = **9,2** | 2,2 ГБ |
| aqe — AQE skew join | 229 с | 42 | 9,7 с / 5,8 с = 1,7 | 2,2 ГБ |
| salt — соль на 16 корзин | 231 с | 45 | 8,7 с / 5,1 с = 1,7 | 2,3 ГБ |
| broadcast | **152 с** | 22, без shuffle | 15,1 с / 8,8 с = 1,7 | 0 |

Что видно:

- Перекос настоящий: без защиты одна задача работает в 9 раз дольше медианы.
- AQE и соль одинаково убирают его по задачам (1,7), AQE — без единой строки
  кода: он сам разрезал перекошенную партицию на части (33 → 42 задачи).
- Но **время стадии не уменьшилось** (107 с без защиты, 120 с с AQE). У кластера
  4 ядра, задач 33, и долгая задача шла параллельно с остальными: узким местом
  была общая работа, а не одна задача. На кластере, где ядер больше, чем задач
  в стадии, долгая задача стала бы хвостом, и борьба с перекосом окупилась бы.
- Справочник ТСП — 20 тыс. строк. Его рассылка убирает перемешивание 2,2 ГБ
  целиком и даёт −25 % времени. Поэтому в рабочем коде broadcast, а соль и AQE
  остаются для случая, когда вторая сторона соединения большая.

## MERGE в ods: отсечение партиций

Один и тот же пакет CDC (47 499 ключей) применён к таблице на 55,7 млн строк
дважды: таблица откатывалась на прежний снимок Iceberg (`rollback_to_snapshot`).

| | MERGE |
|---|---|
| `ON t.txn_id = s.txn_id` | 36,2 с |
| `+ AND t.txn_ts >= <самая ранняя операция пакета>` | **7,1 с** |

Результат одинаковый: число строк, сумма версий, число удалений и сумма операций
совпадают до копейки. По History Server: без условия стадия чтения таблицы —
22 задачи (все месячные файлы) и 55,7 млн записей, с условием — 2 задачи и
3,7 млн записей. Байтов при этом немного (68 и 36 МБ на всё приложение): для
поиска совпадений Iceberg читает только колонки ключа и условия.

## Обслуживание Iceberg и raw

- `rewrite_data_files` на ods: у `card_transactions` 25 файлов данных → 22.
- Висячий файл удалений (125 тыс. позиций, его файл данных уже переписан)
  остался в метаданных после обычного `rewrite_data_files` и ушёл только с
  `remove-dangling-deletes`.
- raw за день: 4 файла на таблицу (по запуску в час) → 1, число строк сверено.

## Ключ распределения факта в Greenplum

Копия факта (55,7 млн строк, AO column zstd, без партиций) с четырьмя ключами
распределения; два сегмента (`scripts/bench_gp.sh`). Перекос — строк на самом
загруженном сегменте к среднему. Время — один прогон.

| Ключ | Перекос | Оборот по дням (SCD2 по client_id) | Клиент × месяц | Соединение с картой |
|---|---|---|---|---|
| txn_id | 1,000 | 26,3 с, 2 Redistribute | 19,8 с, 2 Redistribute | 18,1 с, 2 Redistribute |
| client_id | 1,005 | **21,5 с**, 1 Redistribute | 20,6 с, без Redistribute | 18,1 с, 2 Redistribute |
| card_id | 1,004 | 25,8 с, 2 Redistribute | 19,4 с, 2 Redistribute | **15,3 с**, 1 Redistribute |
| merchant_id | **1,205** | 30,1 с | 22,9 с | 18,0 с |

Что видно:

- Когда ключ распределения совпадает с ключом соединения, из плана уходит одно
  перемещение данных, и запрос быстрее на 16–18 % (client_id для соединения с
  SCD2 клиентов, card_id для соединения с картами).
- Группировка по client_id при распределении по client_id идёт без
  перераспределения вовсе, но быстрее не стала: при двух сегментах запрос
  упирается в подсчёт `count(distinct mcc)`, а не в пересылку.
- Плохой ключ (merchant_id, у одного значения четверть строк) даёт 60 % данных
  на одном сегменте, и все запросы медленнее на 14–16 %: запрос ждёт самый
  загруженный сегмент.
- Факт оставлен распределённым по txn_id: идеально ровно, и инкремент
  delete+insert по txn_id идёт на сегментах локально. Если витрина оборота
  станет узким местом, client_id даёт −18 % на ней; цену для delete+insert
  тогда надо будет замерить отдельно.
